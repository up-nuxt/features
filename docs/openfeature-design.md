# Milestone 3 · Phase 1 · OpenFeature integration design

Status — proposal for review. Research and experiments verified on 2026-11-19 against main at `80fbf38`.

## 1. Existing architecture

The scanner resolves explicit App and Server scopes and discovers declarations, including direct project-root groups. The Registry validates canonical ownership and merges compatible structural declarations across roots. A structural Feature or Group has one logical ID and parent regardless of where its resources live. The shared routing policy walks those parents to decide which URL segments to emit. Flag bindings can consume the same IDs and parents without changing discovery, merge order, routing prefixes or registration. [Architecture](architecture.md) · [Scanner](../src/core/scanner.ts) · [Registry](../src/core/registry.ts) · [Routing policy](../src/core/routing.ts)

Pages Integration resolves concrete route occurrences and views, then publishes an immutable Nuxt-instance snapshot at `app:templates`. Each recognized source includes structural ancestry and exact native Group membership. The snapshot augments the Registry with native page declarations. Nitro Integration publishes a separate Nitro-instance snapshot of Feature server registrations with owner, ancestors, kind, file, route, method and environment. A route occurrence ID embeds filesystem details and can change with path or route name. Nitro provenance covers Feature registrations. These snapshots supply build-time inputs for availability and should stay internal. [Pages integration](../src/integrations/pages.ts) · [Route membership](../src/integrations/page-membership.ts) · [Nitro integration](../src/integrations/server.ts)

## 2. Verified SDK behavior

The installed npm `latest` packages in the isolated fixture were server SDK **1.23.0** and Web SDK **1.10.0**, each with `@openfeature/core` **1.12.0**. Their manifests specify a `^1.12.0` core peer. The server manifest requires Node 20 or newer. The repository uses Node 24 or 26, Nuxt 4.6.4, Nitro 2.13.6 and H3 1.15.11. Local experiments used Node 24.22.2. [JS SDK releases](https://github.com/open-feature/js-sdk/releases) · [Server manifest](https://github.com/open-feature/js-sdk/blob/server-sdk-v1.23.0/packages/server/package.json) · [Web manifest](https://github.com/open-feature/js-sdk/blob/web-sdk-v1.10.0/packages/web/package.json) · [Repository baseline](architecture.md)

| Capability | Server SDK | Web SDK |
| --- | --- | --- |
| Typed evaluation | Async boolean, string, number and object value or details methods. Accepts context per invocation. | Sync boolean, string, number and object value or details methods against the provider's current context and data. |
| Context | Global → transaction → client → invocation → fields from `before` hooks. The optional AsyncLocalStorage transaction propagator must be installed on the API. | Static global or domain-level context. An explicit domain context replaces the inherited global context for that domain. `setContext` can reconcile asynchronously. |
| Lifecycle | Await initial registration with `setProviderAndWait`. Provider replacement and shutdown go through the SDK. | Await initial registration, optionally with initial context. Reconciliation errors are reported via provider status/events even when `setContext` fulfills. |
| Hooks and events | SDK handles API, client, invocation and provider hooks. Client events can track readiness, errors, stale state and configuration changes. | Synchronous evaluation hooks and additional reconciliation/context-change events. |

The evaluation methods take typed defaults and return them on abnormal evaluation. Details can include a reason, error code, variant and metadata. Startup failures are separate from evaluation failures. In the pinned JS releases, clients explicitly block evaluation in `NOT_READY` and `FATAL`. Applications that require fresh values must also decide how to handle `ERROR`, `STALE` and Web `RECONCILING`. Provider events can omit changed keys. OpenFeature runs `before` hooks from API to client to invocation to provider, with the reverse order for `after`, `error` and `finally`. [Evaluation spec](https://openfeature.dev/specification/sections/flag-evaluation/) · [Context spec](https://openfeature.dev/specification/sections/evaluation-context/) · [Hooks spec](https://openfeature.dev/specification/sections/hooks/) · [Events spec](https://openfeature.dev/specification/sections/events/) · [Server implementation](https://github.com/open-feature/js-sdk/blob/server-sdk-v1.23.0/packages/server/src/client/internal/open-feature-client.ts) · [Web implementation](https://github.com/open-feature/js-sdk/blob/web-sdk-v1.10.0/packages/web/src/open-feature.ts)

Both SDKs ship distinct `globalThis` singletons with private API constructors. Spec v0.9.0 describes isolated instances, but these JS release manifests export only their package roots and the isolated API is tracked upstream. Domains scope provider selection. An unbound domain inherits the default provider. API hooks and parts of API configuration remain shared. Registering a replacement publishes it before initialization finishes, may close the preceding provider asynchronously, and leaves a failed replacement bound. Re-registering the same instance can resolve immediately while its original initialization is in flight. Per-domain unregister is unavailable. `close()` and `clearProviders()` affect the singleton, and the released `close()` retains bindings. [Isolated API spec](https://openfeature.dev/specification/sections/flag-evaluation/#18-isolated-api-instances) · [JS isolation issue](https://github.com/open-feature/js-sdk/issues/1373) · [Shared SDK source](https://github.com/open-feature/js-sdk/blob/core-v1.12.0/packages/shared/src/open-feature.ts) · [JS shutdown issue](https://github.com/open-feature/js-sdk/issues/1374)

## 3. Proposed provider integration

**Accept an application-owned OpenFeature server client.** The app registers its chosen provider and supplies its client through a Nitro-only runtime module. The module can reuse an existing client or create one on an explicitly bound app-owned domain. Host apps sharing a JS realm should use distinct, stable app-owned domains where they need separate provider bindings. Sharing the default provider is the host's explicit choice. Require the factory to await readiness before returning the client. The features integration holds one boot-scoped result per Nitro app, coalesces initialization, and uses binding defaults if the factory is absent, rejects or misses the configured startup deadline. This supports the SDK's in-memory provider, a local provider, or any supported third-party provider. Log unexpected initialization failures on the server without including context. Use one bounded attempt per runtime boot and require a fresh boot for a module-managed retry. The application can manage provider recovery after a successful handoff.

The proposed integration leaves domain registration, global hooks, transaction propagators and provider disposal with the application. It releases its own runtime references, subscriptions and pending refresh work on close or HMR. An app that owns its provider can use the Nitro runtime `close` hook or the host's shutdown path, with idempotent cleanup and a deadline. Keep one owner of provider disposal. A host that uses SDK domain replacement must account for asynchronous completion and for a provider shared across bindings. Only an app that owns the whole singleton can decide to run global shutdown. Nitro 2.13.6 invokes runtime plugins synchronously and ignores returned promises. Publish a shared readiness promise from synchronous plugin setup and await it where decisions are needed. Nitro's Node server and dev worker call the runtime close hook through different paths. Verify lifecycle on the target preset. [Nitro v2 runtime](https://github.com/nitrojs/nitro/blob/v2.13.6/src/runtime/internal/app.ts) · [Node shutdown](https://github.com/nitrojs/nitro/blob/v2.13.6/src/runtime/internal/shutdown.ts) · [Dev worker](https://github.com/nitrojs/nitro/blob/v2.13.6/src/presets/_nitro/runtime/nitro-dev.ts)

| Provider ownership option | Assessment |
| --- | --- |
| Application supplies a ready client | Recommended. Reuses existing provider lifecycle and lets the module operate without SDK global mutations. |
| Module owns a provider in a named domain | Possible with a stable app-specific domain, a readiness gate and coordinated teardown. Replacement and the lack of unregister make restart and teardown more complex. |
| Module creates an isolated SDK instance | Revisit when an official released factory is available. Unique domain names provide provider-binding isolation within the singleton. |

## 4. Proposed configuration and binding semantics

Illustrative config for review. With `enabled` omitted or false, setup skips the flags integration and does not resolve an SDK or runtime entry. The runtime path resolves from the consumer's project or a documented Nuxt alias and is imported by Nitro only.

```ts
export default defineNuxtConfig({
  feature: {
    flags: {
      enabled: true,
      serverClient: './server/feature-client.ts',
      bindings: {
        shop: { key: 'features.shop.enabled', defaultValue: false, expose: true },
        'shop/checkout': { key: 'features.shop.checkout', defaultValue: false },
        '@pages/(dashboard)': { key: 'ui.dashboard', defaultValue: false },
        '@pages:feature/shop/(dashboard)': { key: 'ui.shopDashboard', defaultValue: false },
      },
    },
  },
})
```

- The binding key is an exact Registry ID with one explicitly assigned boolean flag. Feature and structural Group IDs already occupy one validated namespace. Native Groups include their Pages namespace and exact relative directory. A nested structural owner is encoded, as in `@pages:feature/shop%2Fcheckout/(dashboard)`. Validate shape, empty flag keys, IDs and origin at build time. Validate native IDs after the resolved Pages snapshot exists. Projects with routing disabled, or Feature Pages registration disabled, get a config error for a native binding whose identity cannot be resolved. Native project groups continue to work with Feature Pages registration off.
- Prefer explicit keys so binding survives route names, aliases, mounts and prefixes, and the provider's naming conventions remain the application's choice. An unbound declaration remains available and contributes no gate. Unknown config IDs fail validation. A runtime typo in a direct declaration lookup should return an explicit error rather than treating the declaration as unbound.
- Effective availability is the logical AND of bound ancestors and the subject's own binding. Follow actual structural links for Features and structural Groups. Follow native Group nesting for native Groups. For a page source combine its structural owner chain with its native Group chain. For a native Group inside a Feature Pages root, the direct Group query also includes the structural chain of the qualified owner. For an entire router match use the union across matched occurrences and named views in that match. Every included binding must pass. A child can add a gate while a disabled parent continues to gate it. Evaluate applicable bindings on every helper call so SDK hooks, current provider state and the complete effective context can affect the result. Preserve each binding’s default.
- Each binding defaults to `false` unless explicitly set to `true`. Missing client, missing flag, type mismatch, initialization failure and abnormal evaluation use that binding's default. For module availability, also use the configured default during SDK `NOT_READY`, `ERROR` and `FATAL` states. Prefer the default when the provider reports `STALE` for a gate, and keep the provider's standard stale-value behavior available through direct SDK calls. The app can choose the default to reflect rollout intent and separately log provider failures. A provider's vendor rules or variants for an existing flag continue to determine its normal value. An app can override a binding's key or default through its resolved Nuxt config. File order, routing overrides and browser context have no precedence over a bound ancestor.
- `expose` defaults to false and permits the browser to request that binding subject's final boolean by its declared public ID. Review exposure of the resulting combined decision, including inherited flags. Route availability responses can expose the combined outcome of an opted-in page without exposing each constituent decision. A direct lookup still requires explicit exposure.

## 5. Runtime context and public interface

On the server, derive context in Nitro from the current H3 event at evaluation time, for example through a named `getEvaluationContext(event)` export next to the client factory. The callback can use already established identity or tenant data after the app's authentication middleware runs. Attach a request evaluator to `event.context`, or bind it through a per-Nitro-app runtime service. SSR uses `useRequestEvent()` to access the same event-backed interface. Capture the event before awaiting work. Pass a fresh invocation context to the borrowed client. Permit trusted server callers to add explicit context, with invocation fields taking precedence for permitted attributes. Treat targeting identity as app-owned and protect intentionally reserved keys from helper overrides. Keep the evaluator on the event and let the SDK resolve the complete context independently for each evaluation. The application can independently use the SDK's AsyncLocalStorage propagator if it owns the outer request dispatch. A Nitro request hook or middleware that scopes only its own callback cannot propagate a context to the later handler. [Nuxt request event](https://nuxt.com/docs/4.x/api/composables/use-request-event) · [Nitro v2 request pipeline](https://github.com/nitrojs/nitro/blob/v2.13.6/src/runtime/internal/app.ts) · [OpenFeature context](https://openfeature.dev/specification/sections/evaluation-context/)

Candidate server interface is `await isFeatureEnabled(event, 'shop', { context })` and `await isGroupEnabled(event, 'shop/checkout', { context })`. Both share one internal availability evaluator and validate the expected declaration kind. Vue consumers use `await useFeatureAvailability('shop')` or `await useGroupAvailability('shop/checkout')` on exposed subjects. Return Nuxt async data with a typed Boolean decision, status and refresh. Route middleware takes the destination's matched records and uses the same evaluator through its server or browser transport. Use ordinary OpenFeature clients for raw boolean, string, number and object flags, variants, tracking, evaluation details and hooks. Availability is the extra behavior the module owns. For tests, pass an SDK in-memory provider or an OpenFeature-client test double to the runtime interface.

TypeScript can enforce binding shape, boolean defaults and public result types from the outset. Exact filesystem-derived ID unions require opt-in generated declarations after discovery and a topology refresh strategy. Begin with validated string keys and preserve literal config keys with `satisfies` where useful. Generated component-side declarations should cover exposed IDs only. A provider-specific flag catalog can narrow vendor keys in application code independently of filesystem identities.

## 6. SSR, browser refresh and rendering modes

The recommended first release evaluates on the server. SSR writes only the public decision to the Nuxt payload for the current request. Serialize a non-null object such as `{ enabled: false }` so both results can be reused. Browser hydration consumes the exact SSR decision even if provider state changed after the response. Nuxt initial route middleware can execute on both server and browser. On hydration, it reads the same seeded decision with the same decision key, or skips a duplicate guard when the server already resolved the route. Later navigations, explicit refresh and identity changes query the same-origin Nitro endpoint. Accept only exposed subject IDs or opted-in page tokens, derive context from the new request, and return minimal decisions. Prevent old responses from winning after route, session or identity changes using cancellation or request generations. Give the browser a fresh decision when its identity changes and clear prior identity data. Reactive consumers can refresh on explicit triggers initially. Streaming server provider events to browsers adds a new transport and can be considered later. [Nuxt async data](https://nuxt.com/docs/4.x/api/composables/use-async-data) · [Nuxt route middleware](https://nuxt.com/docs/4.x/directory-structure/app/middleware)

A later client-only adapter can integrate the Web SDK for flags the app intentionally evaluates in the browser. Keep it in a separate `.client` entry. Use an application-owned domain with explicit browser-safe context. Place Web provider setup after the initial SSR decision is seeded and wait until hydration before applying browser reevaluations. React to ready, configuration-changed and context-changed events, remove listeners on disposal, and defer updates while reconciling. An identity change should replace the domain context, hold pending/default values while it reconciles, and ignore stale results. Server decisions remain authoritative for server-rendered data and Nitro operations. Apps needing fully static hosting can use browser-only UI flags, or public context-invariant build decisions. A user-targeted SSR gate requires a running server and request context. [Web SDK](https://openfeature.dev/docs/reference/technologies/client/web/) · [Nuxt rendering modes](https://nuxt.com/docs/4.x/guide/concepts/rendering)

## 7. Route availability and failure policy

| Surface | Recommended first policy |
| --- | --- |
| Components and pages | Keep routes registered. Expose decisions for conditional UI and fallback content. |
| Nuxt route middleware | Offer opt-in guards later. A disabled page can return HTTP 404 on an SSR entry and show Nuxt's 404 error on client navigation. Redirects require an explicit loop-safe destination. Component fallback remains an application rendering choice. Leave redirects and custom router entries outside automatic coverage until their semantics are verified. |
| Nitro API and server routes | Start with explicit per-handler checks after IAM and before the flagged operation. Offer opt-in generated wrappers for registered Feature API/route handlers only after verifying provenance, route rules, method, environment and lazy handler behavior. Both direct and internal requests require the same server check. |
| Nitro middleware and plugins | Keep global behavior. An app can explicitly branch on availability within their authored logic. |

Runtime default `false` keeps a rollout unavailable when a decision cannot be resolved. Applying this to an opted-in guard returns its configured unavailable response. Return 503 for an outage only if a future policy deliberately distinguishes an operational failure from a disabled flag using detailed results. This allows ordinary defaults to remain deterministic. The flags integration manages rollout availability. IAM, authentication and resource authorization stay under application control. Clients can inspect a page bundle or bypass its navigation guard, so server data and actions require independent policy checks.

Treat personalized page HTML, payloads and decision responses as private and avoid shared CDN, Nitro cached handlers, SWR, or static prerendering for those results. A per-request check inside a cached handler can be bypassed on cache hits. A generated wrapper must sit outside shared caching or reject a conflicting caching policy. Context, raw provider keys, override inputs, rule sets, error details, provider or session credentials and absolute paths stay on the server. Validate public lookup IDs against the allowlist, use a versioned per-build page-token map, and return only decisions intentionally visible to that browser. A token identifies a route occurrence and grants no access. Restrict context attributes to the minimum needed and avoid forwarding user-supplied context from browser requests.

## 8. Smallest build-time extension and package boundaries

Keep `src/core` independent and reuse the Registry and the existing snapshots. Add a build-time flags integration that compiles an immutable ID-to-binding table and the small server runtime projection each adapter needs. For explicit server calls the binding table and Registry ancestry are sufficient. For future automatic Pages guards, reuse the route occurrence-to-source relationship at template generation to attach a reserved, opaque token to each opted-in generated route record. Derive the token per build without embedding paths, names, flag keys or provenance; version the projection for stale tabs and HMR. At runtime read tokens from individual `to.matched` records so a child cannot overwrite a parent's membership through the merged meta object. Preserve authored metadata by reserving and validating one key. Verify build hook order, alias behavior, named views, nested records, macro re-evaluation and custom static metadata options before enabling this. Report unsupported dynamic routes as outside automatic coverage. [Nuxt 4.6.4 route generation](https://github.com/nuxt/nuxt/blob/v4.6.4/packages/nuxt/src/pages/utils.ts) · [Pages membership implementation](../src/integrations/page-membership.ts)

An implementation may add an internal correlation from the resolved `NuxtPage` object to its occurrence during the same template generation, so runtime matching need never reconstruct an ID from a filename or URL. For potential Nitro wrappers, consume the validated registration directly inside the Nitro integration and preserve all registration fields. Lookup by exact handler record and mode before bundling, so there is no URL-based provenance reconstruction at runtime. Core and existing snapshot contracts suffice for explicit evaluation. No public Registry API is needed for this work.

Use a Nitro-only runtime entry and an SDK-free universal entry for Nuxt transport and presentation. Resolve the optional server entry only when enabled and configured. Use `@openfeature/server-sdk` as an optional peer if its client types appear in the opt-in entry declarations. Keep that import out of the root module and universal type graph so projects without the peer can still type-check. The adapter can accept a type-only subset of the SDK client and let the consuming app import the SDK and provider. Include a package-consumer fixture to check pnpm peer resolution and package exports. If a Web adapter is approved, expose it through a distinct optional browser entry and add `@openfeature/web-sdk` as an optional peer then. The SDKs declare their core peer. The consumer should install a compatible core package as required by its package manager. Run packaging and leak checks against Nuxt 4.6.4 with Nitro 2.13.6 first. Report other Nitro majors, builders and edge presets as separate compatibility work.

## 9. Feasibility results

The SDKs were installed in a temporary directory. The disposable fixture used the repository's Nuxt and Nitro dependencies and the existing Features module. It built with the Nitro `node-listener` preset, which let the test submit overlapping H3 requests via the compiled listener in one process. The synthetic request header supplied distinct test identities.

| Experiment | Observed result |
| --- | --- |
| Server lifecycle and fallback | The isolated SDK script returned the typed fallback without a provider, during delayed initialization, after a failed registration, and for a missing flag. Initializing the same instance twice while startup was pending called `initialize` once. A second registration call returned before the first was ready. Two explicitly bound domains returned opposite decisions. An unbound domain inherited the configured default provider. Replacing one domain triggered its provider's close hook and left the default client's decision intact. |
| Web evaluation and context | The Web SDK ran in Node for this SDK-only check. Boolean, string, number and object resolution returned the expected values synchronously. The provider received the initial domain context and the subsequent domain context update. A missing flag returned the supplied default. |
| Concurrent Nitro handlers | Delayed overlapping evaluations produced `true` and `false` for different invocation contexts. A third request induced a provider exception and returned `false`. Each received its own result. |
| Canonical membership and route metadata | The production build resolved `@pages/(dashboard)` and `@pages:feature/shop/(dashboard)` as distinct groups. A template hook emitted an opaque token alongside authored metadata for the native route. SSR via its authored alias retained both values. |
| SSR decisions and payload | Concurrent SSR requests rendered opposite decisions. Both HTML responses contained the expected decision payload and omitted the fixture targeting identities, provider name and key. |
| Browser hydration | Headless Chrome mounted the page through its authored alias and retained the server's `true` decision after hydration. The client-side fetcher in this fixture would otherwise return `false`. The test measured the mounted DOM and preserved route metadata. |
| Client build artifact | Searched the emitted public files for the synthetic provider key, SDK package identifier, domain and context header. None appeared. The opaque route token and alias appeared in the client build. |
| Repository regression tests | **130 passed** across `core`, `registry`, `page-membership`, `routing-policy`, `pages.integration` and `server.integration`. The first sandboxed run denied loopback for 13 HTTP tests. The rerun with loopback access passed all six files. |

The feasibility checks cover the proposed building blocks on the pinned Node runtime. The browser probe covered one initial navigation. Future integration tests should exercise real provider recovery and HMR teardown, browser identity changes and client navigation, cache conflicts, a consumer without any SDK installed, and build-output inspection for the packaged integration.

## 10. Implementation phases after design approval

1. Add build-time binding validation for structural and native Group IDs and a pure inherited-availability policy. Test unbound declarations, kind validation, merged roots, qualified Groups and ancestor defaults.
2. Add the Nitro-only client seam and event-backed server helpers. Validate request concurrency, readiness and failure, runtime close behavior, and a packed consumer with and without the optional SDK. Use the helper from Feature and native handlers.
3. Add opt-in public decisions, Nuxt SSR/composables and a same-origin refresh endpoint. Test hydration for both decisions, refresh after identity changes, disabled flags during client navigation, and private cache and payload behavior.
4. If approved, add explicit Pages guards and Feature Nitro wrappers. Verify metadata hooks, nested and named views, aliases, server cache ordering and independent authorization. Evaluate a browser-only Web SDK adapter separately if a concrete use case requires one.

## 11. Decisions for approval

- Use the app-owned server client seam and host-owned disposal, with a bounded readiness wait and binding defaults on initialization failure.
- Accept the proposed binding shape and explicit IDs. Adopt an AND across structural and native ancestry, default `false`, and per-subject client exposure.
- Use Nitro as the decision authority for SSR and client navigation. Approve the scope of the public refresh endpoint, including which decisions can be sent to browsers. Defer a Web SDK adapter to a separate phase.
- Begin with conditional UI and explicit handler checks. Decide whether automatic availability guards should be added later, including the all-views policy for matched records and 404 versus app-directed fallback.
- Approve the initial compatibility target and the type and package surface before adding any SDK peer dependency.
